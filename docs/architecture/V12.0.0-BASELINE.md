# RuleForge V12.0.0 - Architectural Baseline

**Status:** Frozen (Stable)
**Date:** October 2024
**Tag:** `v12.0.0`

This document serves as the architectural baseline for RuleForge V12.0.0. It records the engineering milestones, core contracts, and limits established up to this version. Any future language evolution (V12.1+ or V13) must respect or formally supersede the guarantees outlined here.

## 1. Evolution Summary (V11.8 → V12.0)

RuleForge evolved through three distinct, disciplined phases:

1.  **V11.8.x (Runtime Optimization):** Focused on eliminating bottlenecks (O(N²) removal, AST caching, O(1) dispatch, conditional deepcopy). All optimizations were profile-driven, and discarded if they showed no end-to-end improvement or violated V11 semantics.
2.  **V11.9.0 (Developer Experience):** Decoupled the Core engine from the HTTP API. Introduced the REPL, CLI (`eval`, `check`, `trace`), and a shared human-readable formatter. Tooling was packaged natively via `pip install .`.
3.  **V12.0.0 (Language Evolution):** Implemented RFC-001 (`MATCH/CASE`) layer by layer (Lexer → AST → Semantic → Evaluator → Trace). Verified against V11 regressions and cross-language conformance at every step.

## 2. RFC-001: MATCH/CASE Invariants

The `MATCH/CASE` structure operates under strict invariants to preserve RuleForge's deterministic and sandboxed nature:

*   **Strict Typed Equality:** No implicit coercion (e.g., `1 != true`). Type must match exactly.
*   **First-Match Wins (Short-Circuit):** The first `CASE` with a matching value is selected. Subsequent `CASEs` and `DEFAULT` are **not evaluated**.
*   **No Fall-Through:** Once a `CASE` is selected, its actions are executed, and the rule terminates.
*   **DEFAULT / NO_ACTION:** If no `CASE` matches, `DEFAULT` executes. If `DEFAULT` is absent, `NO_ACTION` is executed.
*   **No `CASE NULL`:** `NULL` is not a valid `CASE` literal. An expression evaluating to `NULL` will never match a `CASE` and will fall through to `DEFAULT` or `NO_ACTION`.
*   **Bounded Execution:** `MAX_CASES_PER_MATCH = 50`.

## 3. Architectural Integration

`MATCH` was integrated into the existing V11 pipeline without altering global dispatch routes:

*   **AST:** `RuleNode` was extended with an optional `MatchNode` property (backward compatible).
*   **Semantic Analyzer:** Validates types, duplicate cases, and limits.
*   **Evaluator:** Evaluates the `MATCH` expression exactly once. Uses lazy evaluation for `CASEs`. Reuses the V11 `SET`/`EMIT` resolution logic, ensuring `SET` patches the `working_context` for subsequent rules in the pipeline.
*   **Compiler:** Supports `MATCH` natively. `Interpreter ↔ Compiler` parity is 100%.

## 4. Trace Contract (V11.3 + V12.0)

The trace strictly represents expression evaluation, not action execution.

*   **V11.3 Contract:** `SET` and `EMIT` actions are resolved and returned in `Decision.actions`. They **do not** create artificial nodes inside the deep trace tree.
*   **V12.0 MATCH Trace:** Constructs a `MatchExpression` root node containing the evaluated expression value. `Case` children represent evaluated cases (`Matched: true/false`) or short-circuited cases (`ShortCircuited: true`, `Reason: short_circuit`). `Default` is marked as `Matched` or `ShortCircuited`.
*   **Error Trace:** If the `MATCH` expression or an evaluated `CASE` fails, the V11.3 `_error_trace` contract captures the error at the failing node.

## 6. Discarded Decisions & Future Considerations

*   **Loops / FOR EACH:** Explicitly deferred. RuleForge's core value proposition includes bounded, non-Turing-complete execution. Adding loops would require a fundamental review of security limits (MAX_EXECUTION_STEPS) and is reserved for a potential V13.
*   **Pattern Matching / Expression CASEs:** Currently, `CASE` only accepts literals. `CASE > 18` is not supported to maintain strict equality semantics and avoid complicating the deterministic type system.
*   **JSON Schema Integration:** A strong candidate for V12.1, provided it can be mapped to the existing schema dictionary without breaking the strict typing contract.

## 7. Rules for Future Language Evolution

1.  **RFC First:** No language feature is implemented without a formal RFC defining syntax, semantics, types, limits, and trace behavior.
2.  **Layer-by-Layer:** Implementation must flow sequentially: Lexer → AST → Semantic → Evaluator → Trace.
3.  **Cross-Language Parity:** Python and C# must produce identical decisions and traces. The gate must remain 100% green at every commit.
4.  **V11 Isolation:** New features must be isolated (like `MatchNode`) and must not require modifying global dispatch tables (`eval_node` / `EvaluateNodeInternal`) if it risks V11 regressions.
